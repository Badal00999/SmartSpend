## D1 — Calendar input silently changes meaning

**Risk:** high data-integrity impact, affecting create, edit, bulk import and query filters.

**Reproduction:** authenticated POST `/api/v1/transactions` with `{title:'Grocery run', amount:2340, type:'expense', category:'food', payment:'upi', date:'2025-02-29', notes:'Weekly vegetables'}`. Expected 422 with a `date` field error. Observed 201 in `red-server.log`. PATCH with `2026-04-31` returned 200, and bulk import containing one invalid date returned 201. In JavaScript, `new Date('2025-02-29T00:00:00Z').toISOString()` becomes `2025-03-01T00:00:00.000Z`.

**Cause:** `server/src/validators/schemas.js` checked format plus a non-NaN Date, which accepts rollover dates. List/statistics query bounds checked only a regular expression. The front-end pure validator checked only missing/future dates, so three new impossible-calendar cases also passed validation unexpectedly. Native date inputs constrain ordinary typing, but the exported validator still needs to reject programmatic/imported values.

**Additional observed query evidence:** `/transactions?from=2026-13-01` and `/stats/summary?...` returned 400 downstream; `/stats/by-category?...` returned 200. The desired contract is one 422 validation envelope before database access, not an incorrect claim that all these endpoints returned 500. Reversed date/amount bounds were also accepted by the original schemas.

**Fix:** create a shared calendar-date schema for server writes/queries, requiring the UTC ISO date to round-trip exactly to the input string. Apply the no-future rule only to writes; future query bounds are valid. Add ordered-date and ordered-amount refinements. Mirror the round-trip check in `client/src/components/transactions/TransactionForm.jsx`.

**Verification:** 18 tests in `server/tests/week5-validation.test.js` (14 initially failing) and 7 tests in `client/src/test/week5-form.test.jsx` (3 initially failing). API tests check both status and the absence of an inserted/modified record. A real leap day `2024-02-29` remains valid. Two added Playwright tests verify UI save/reload and same-origin invalid-date rejection. `evidence/screenshots/leap-day-ui.png` is generated by the valid-date test.

**Lesson:** a syntactically ISO-shaped string and a constructible Date are not sufficient calendar validation. Test both the reject boundary and the valid neighbouring leap-day case.

## D2 — Timeout ends at headers instead of the full response

**Risk:** a partially responding service leaves the UI request pending indefinitely.

**Reproduction:** in `client/src/test/week5-api.test.js`, the fetch stub resolves with status 200 immediately, but its JSON reader waits until its AbortSignal fires. Call `request('/health', {timeoutMs:50,retries:0})`; advance fake time by 60 ms. Expected `TIMEOUT`; observed `pending` in `red-client.log`.

**Cause:** `client/src/services/api.js` invoked `guard.done()` after `await fetch(...)`, before `await res.json()`. Fetch resolves when headers arrive, not when the body has finished. The body reader had no active deadline.

**Fix:** move JSON reading inside the guarded try block; release timer/listener only after reading or catching a failure. Preserve the abort reason so timeouts do not become generic HTTP errors. Syntax errors still become an HTTP_ERROR; 204 returns null without reading JSON.

**Verification:** stalled-body test now produces `TIMEOUT`. Other transport tests confirm 204 handling, malformed JSON, bounded retries and timer cleanup. These are controlled fake-timer tests, not measured Internet response times. The default 12-second timeout remains per attempt: up to three GET attempts can take longer than 12 seconds overall.

**Lesson:** a request lifecycle includes response-body consumption; test that boundary explicitly rather than only mocking a fetch that never resolves.

## D3 — Cancellation does not stop retry work promptly

**Risk:** obsolete component requests continue unnecessary retry work after navigation/unmount.

**Reproduction:** reject the first fetch with a network error, abort the caller's controller after 10 ms while the request waits in its 250 ms backoff, then advance timers. The original transport invoked the fetch mock twice rather than once.

**Cause:** the sleep helper ignored cancellation, and the retry loop had no early aborted-signal check.

**Fix:** make the backoff Promise abort-aware; clear its timer and listener when cancelled. Check the caller signal at each loop entry. Only GET requests retry network failures; mutation retries are not enabled.

**Verification:** same regression test now asserts exactly one fetch invocation and an AbortError. This demonstrates no second fetch invocation in the controlled test; it does not claim the old browser necessarily transmitted a second HTTP request, since native fetch may reject an already-aborted signal before network I/O.

**Lesson:** cancellation applies during waits as well as active network operations.

## D4 — SSE authentication token appears in access logs

**Risk:** bearer credentials exposed to log readers; a privacy/security issue discovered during evidence review.

**Observed evidence:** the first successful E2E run included an access log shaped as `GET /api/v1/events/stream?token=[REDACTED] 200 ...`. The saved evidence was sanitized before packaging; original JWTs are not supplied.

**Cause:** `server/src/app.js` used Morgan's dev/combined formats, which include the original URL. EventSource sends its JWT in the query string. Combined format may also log Referer, which can contain sensitive query values.

**Fix:** `server/src/middleware/requestLogger.js` logs method, path before `?`, status, duration and request ID only. No query values or Referer. The app uses this formatter in development/production. A separate evidence sanitizer removes JWTs and token query values from already captured files.

**Verification:** four middleware tests first ran against the old Morgan dev format and failed on the presence of `private-test-value`; they now pass for normal, duplicated/mixed-case, percent-encoded and arbitrary query keys. Captured final E2E lines show `/api/v1/events/stream 200 ... requestId=...` with no token.

**Trade-off:** removing query values reduces search-filter diagnostics; request IDs retain traceability. This does not remove the token from the browser URL or an upstream proxy's logs. Production proxies must also redact it, and a future cookie/short-lived stream-ticket design needs its own CSRF/security review.

## P1 — Query planner performs a blocking sort

The API already sorted by date plus `_id` for stable pages, but the index stopped at date. Explain output showed a SORT and 10,000 documents examined for 20 results. The schema index now includes `_id`. See `PERFORMANCE.md` for raw samples, ordered-ID equality checks, exact methodology and limits. This is a measured optimization, not an invented functional bug.
